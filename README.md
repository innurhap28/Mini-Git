# Mini Git

Python으로 구현한 CLI 기반 Mini Git

Git의 핵심 구조인 **커밋 그래프, 브랜치, 커밋 탐색, 역색인, 정렬 알고리즘**을 직접 구현하여 Git의 내부 동작 원리를 이해하는 것을 목표로 합니다.

## 1. 프로젝트 소개

Mini Git은 실제 Git의 파일 추적이나 네트워크 기능을 구현하는 대신, 커밋의 메타데이터와 커밋 간 관계를 메모리에서 관리합니다.

주요 기능은 다음과 같습니다.

* 저장소 초기화
* 브랜치 생성 및 전환
* 커밋 생성
* 커밋 로그 출력
* 커밋 간 최단 경로 탐색
* 커밋의 조상 탐색
* 키워드 및 작성자 기반 검색
* 날짜 및 작성자 기준 로그 정렬
* CLI REPL 환경 제공

> 파일 내용 추적이나 실제 Git 저장소와의 연동은 구현하지 않습니다.

## 2. 실행 방법

Python 3 환경에서 실행합니다.

```bash
python3 main.py
```

실행하면 다음과 같은 CLI 환경이 시작됩니다.

```text
mini-git>
```

`exit` 또는 `quit`을 입력하면 프로그램을 종료할 수 있습니다.

모든 데이터는 메모리에 저장되므로 프로그램을 종료하면 저장된 커밋과 브랜치 정보도 초기화됩니다.

## 3. 프로젝트 구조

```text
B3-2/
├── main.py
├── mini_git.py
├── repository.py
├── commit.py
├── branch.py
├── graph.py
├── search.py
├── sort.py
└── README.md
```

### 파일별 역할

| 파일              | 역할                                             |
| --------------- | ---------------------------------------------- |
| `main.py`       | 프로그램 진입점 및 CLI REPL 실행                         |
| `mini_git.py`   | Repository, Graph, Search, Sort를 연결하는 핵심 인터페이스 |
| `repository.py` | 커밋과 브랜치 저장 및 관리                                |
| `commit.py`     | Commit 객체 정의                                   |
| `branch.py`     | Branch 객체 정의                                   |
| `graph.py`      | DFS, BFS, 위상 정렬 및 커밋 그래프 탐색                    |
| `search.py`     | 키워드/작성자 역색인 관리 및 검색                            |
| `sort.py`       | 직접 구현한 정렬 알고리즘                                 |
| `README.md`     | 프로젝트 설명 및 사용 방법                                |

알고리즘 로직은 각각 독립된 클래스와 함수로 분리하여 CLI와 핵심 로직의 역할을 구분했습니다.

## 4. 주요 명령어

### 저장소 및 브랜치

| 명령어                    | 설명                              |
| ---------------------- | ------------------------------- |
| `INIT <user_name>`     | 저장소를 초기화하고 `main` 브랜치와 HEAD를 생성 |
| `BRANCH <branch_name>` | 현재 HEAD를 가리키는 새로운 브랜치 생성        |
| `SWITCH <branch_name>` | 지정한 브랜치로 HEAD 이동                |
| `COMMIT <message>`     | 현재 HEAD를 부모로 하는 새로운 커밋 생성       |

문자열 인자에 공백이 포함되는 경우 따옴표를 사용합니다.

```text
INIT "Alice"
COMMIT "Add login feature"
```

### 로그 및 그래프 탐색

| 명령어                        | 설명                      |
| -------------------------- | ----------------------- |
| `LOG`                      | 부모 커밋이 자식 커밋보다 먼저 출력    |
| `PATH <commit1> <commit2>` | 두 커밋 사이의 최단 경로 탐색       |
| `ANCESTORS <commit_hash>`  | 특정 커밋에서 도달 가능한 모든 조상 탐색 |

`PATH`에서는 커밋과 부모의 연결을 **무방향 그래프의 간선**으로 취급합니다.

### 검색 및 정렬

| 명령어                      | 설명                   |
| ------------------------ | -------------------- |
| `SEARCH <keyword>`       | 커밋 메시지의 키워드로 검색      |
| `SEARCH --author=<name>` | 작성자로 커밋 검색           |
| `LOG --sort-by=date`     | timestamp 기준으로 로그 정렬 |
| `LOG --sort-by=author`   | author 기준으로 로그 정렬    |

기본 `LOG`는 **커밋 간 부모-자식 관계를 만족하는 순서**를 만들기 위한 위상 정렬 방식으로 동작하며, `--sort-by`가 지정된 경우에는 해당 기준에 따라 직접 구현한 정렬 알고리즘을 적용합니다.

## 5. 커밋 구조

하나의 커밋은 다음 정보를 가지고 있습니다.

```text
Commit
├── hash
├── message
├── author
├── timestamp
└── parents
```

예를 들어:

```text
A
↓
B
↓
C
```

각 커밋은 자신의 부모 커밋을 `parents`에 저장합니다.

```text
A.parents = []
B.parents = [A]
C.parents = [B]
```

브랜치는 특정 커밋을 가리키는 포인터 역할을 하며, HEAD는 현재 브랜치를 가리킵니다.

```text
HEAD
 ↓
main
 ↓
Commit C
```

### 초기 상태

`INIT`를 실행하면 새로운 저장소가 생성되고 `main` 브랜치와 HEAD가 설정됩니다.

```text
Repository
├── commits = {}
├── branches
│   └── main → None
└── HEAD → main
```

이후 `COMMIT`을 실행하면 현재 HEAD를 부모로 하는 새로운 커밋이 생성되고 해당 브랜치가 새로운 커밋을 가리키도록 이동합니다.

## 6. 커밋 Hash

각 커밋은 고유한 hash를 식별자로 사용합니다.

```text
commits
├── "2fbabb" → Commit
├── "bac465" → Commit
└── "be4730" → Commit
```

커밋 hash를 dictionary의 key로 사용하기 때문에 hash를 알고 있다면 커밋을 빠르게 조회할 수 있습니다.

현재 구현에서는 UUID 기반의 값을 생성한 뒤 일부를 잘라 커밋 hash로 사용합니다.

```text
UUID 생성
   ↓
문자열 변환
   ↓
앞부분 일부 사용
   ↓
Commit hash
```

### Hash 충돌

hash의 길이를 짧게 만들면 서로 다른 커밋이 같은 hash를 가질 가능성이 발생할 수 있습니다.

따라서 현재 구현에서는 커밋 생성 시 기존 저장소의 hash와 중복되지 않는지 확인하여 **하나의 실행 세션 내에서 hash가 중복되지 않도록 관리**합니다.

과제에서 요구하는 것도 세션 내 커밋 hash의 유일성이며, 구현 방식은 자유롭게 선택할 수 있습니다.

다만 짧은 hash는 hash 공간이 작아질수록 충돌 확률이 증가합니다. 실제 대규모 시스템이라면 더 긴 hash를 사용하거나 충돌 검사를 수행하고, 필요하다면 충돌 시 새로운 hash를 다시 생성하는 방식으로 대응할 수 있습니다.

### Hash 생성 방식의 재현성

현재 UUID 기반 방식은 실행할 때마다 새로운 값을 생성하므로 동일한 입력을 사용해도 동일한 hash가 만들어진다는 보장이 없습니다.

따라서 테스트에서 특정 hash를 고정하여 비교하기에는 불편할 수 있습니다.

대안으로는 다음과 같은 방법을 사용할 수 있습니다.

* 세션 내 증가하는 counter를 이용한 hash 생성
* 충분히 긴 랜덤 값을 사용하는 방식
* 커밋 내용과 부모 hash 등을 이용한 결정적 hash 생성

현재 프로젝트에서는 학습 목적상 구현이 단순한 UUID 기반 방식을 사용하고, 세션 내 중복이 발생하지 않도록 관리합니다.

## 7. DAG 구조와 커밋 이력

커밋 그래프는 **DAG(Directed Acyclic Graph, 방향성 비순환 그래프)** 형태로 관리합니다.

각 커밋은 이미 존재하는 부모 커밋을 가리킵니다.

```text
A
↓
B
↓
C
```

새로운 커밋은 기존 커밋에서 생성되므로 일반적인 COMMIT 과정에서는 이미 생성된 커밋을 다시 가리키는 순환 구조가 만들어지지 않습니다.

브랜치가 분기되면 다음과 같은 구조가 됩니다.

```text
        B ── C
       /
A ───
       \
        D ── E
```

여러 브랜치가 하나의 부모 커밋에서 분기될 수 있지만, 커밋의 부모 관계가 과거 방향으로만 연결되기 때문에 DAG 구조를 유지할 수 있습니다.

### Cycle 문제

커밋 그래프에 순환(cycle)이 발생하면 위상 정렬이나 조상 탐색 등의 그래프 알고리즘이 정상적으로 동작하지 않을 수 있습니다.

따라서 커밋 생성 과정에서 임의의 커밋을 부모로 설정하여 기존 그래프에 순환을 만드는 방식은 허용하지 않고, 현재 HEAD를 부모로 하는 방식으로 커밋을 생성합니다.

### 커밋 이력의 불변성

커밋이 생성된 이후에는 해당 커밋의 부모 관계와 메타데이터를 변경하지 않습니다.

브랜치가 이동하는 것은 커밋 자체를 변경하는 것이 아니라 **브랜치가 가리키는 커밋을 변경하는 것**입니다.

```text
Commit A ← 변경하지 않음
    ↑
main → Commit B
```

따라서 새로운 작업이 발생하면 기존 커밋을 수정하는 대신 새로운 커밋을 생성하여 이력을 이어갑니다.

## 8. Repository

`Repository`는 Mini Git의 전체 상태를 관리합니다.

```python
self.commits = {}
self.branches = {}
self.head = None
self.current_user = None
```

### Commit 저장

커밋은 hash를 key로 사용하는 dictionary에 저장합니다.

```text
commits
├── "2fbabb" → Commit
├── "bac465" → Commit
└── "be4730" → Commit
```

따라서 commit hash를 이용하여 커밋을 빠르게 조회할 수 있습니다.

평균적인 dictionary 조회는 O(1)의 시간복잡도를 기대할 수 있으므로, hash를 이용한 커밋 조회에 적합합니다.

### Branch 관리

브랜치는 이름과 현재 가리키는 커밋 hash를 가지고 있습니다.

```text
branches
├── main    → be4730
└── feature → adc2b9
```

HEAD는 현재 브랜치 이름을 저장합니다.

```text
HEAD → main → be4730
```

`SWITCH`는 커밋을 이동시키는 것이 아니라 HEAD가 가리키는 브랜치를 변경합니다.

## 9. 커밋 그래프 탐색

`graph.py`에서는 커밋 간 부모 관계를 이용하여 그래프 탐색 기능을 구현합니다.

그래프 탐색에 필요한 공통 로직은 다음과 같이 분리했습니다.

```text
Graph
├── _dfs()
├── _bfs_path()
├── _topological_sort()
├── _get_parents()
└── _get_neighbors()
```

각 명령은 이러한 공통 탐색 로직을 조합하여 사용합니다.

### ANCESTORS

특정 커밋에서 부모 방향으로 이동하면서 모든 조상 커밋을 탐색합니다.

DFS(깊이 우선 탐색)를 사용합니다.

```text
C
↓
B
↓
A
```

`ANCESTORS C`를 실행하면 `B`, `A`와 같이 C에서 부모 방향으로 도달 가능한 커밋을 찾습니다.

이미 방문한 커밋은 `visited` 집합에 기록하여 중복 탐색을 방지합니다.

### PATH

두 커밋 사이의 최단 경로를 찾기 위해 BFS(너비 우선 탐색)를 사용합니다.

커밋의 부모 관계를 다음과 같이 무방향 간선으로 취급합니다.

```text
A ─ B ─ C
    │
    D
```

따라서 부모 방향뿐만 아니라 자식 방향으로도 이동할 수 있습니다.

BFS는 시작점에서 가까운 노드부터 탐색하기 때문에 간선의 가중치가 모두 동일한 현재 그래프에서 최단 경로를 찾을 수 있습니다.

최단 경로가 여러 개 존재하는 경우에는 이웃 커밋을 hash의 사전순으로 탐색하여 경로를 구성합니다.

과제의 tie-breaking 규칙에 따라 `hash1->hash2->...` 형태의 경로 문자열을 비교했을 때 사전순으로 가장 작은 경로를 선택하는 것을 목표로 합니다.

최단 경로가 존재하지 않는 경우에는 다음을 출력합니다.

```text
No path
```

### LOG

`LOG`에서는 일반적인 최신순 출력이 아니라 **부모 커밋이 자식 커밋보다 먼저 출력되는 순서**를 사용합니다.

예를 들어:

```text
A
↓
B
↓
C
```

출력 순서는 다음과 같습니다.

```text
A
B
C
```

이를 위해 `graph.py`의 `_topological_sort()`에서 Kahn의 알고리즘을 기반으로 부모가 먼저 처리되도록 순서를 구성합니다.

각 커밋의 미처리 부모 수를 관리하고, 부모가 모두 처리된 커밋을 순서대로 queue에 추가합니다.

이 방식으로 다음 조건을 만족합니다.

```text
부모 처리
   ↓
자식 처리
   ↓
더 하위 자식 처리
```

## 10. 역색인(Inverted Index)

커밋 검색에서는 모든 커밋을 하나씩 순회하는 대신 **역색인(Inverted Index)**을 사용합니다.

`search.py`에서는 두 종류의 인덱스를 관리합니다.

```text
keyword_index
keyword → commit_hash 목록

author_index
author → commit_hash 목록
```

예를 들어 다음과 같은 커밋이 존재한다면:

```text
A: Initial commit
B: Add login feature
C: Fix login bug
```

키워드 `login`은 다음과 같이 관리할 수 있습니다.

```text
login → [B, C]
```

따라서 `SEARCH login`을 수행하면 모든 커밋을 순회하는 대신 `login`에 해당하는 hash 목록을 먼저 가져올 수 있습니다.

### 키워드 정규화

커밋 메시지를 공백 기준으로 분리하고 소문자로 변환하여 키워드를 저장합니다.

```text
"Add Login Feature"
```

↓

```text
add
login
feature
```

즉, 최소 기준은 다음과 같습니다.

```python
message.split()
```

그리고 각 토큰을 소문자로 정규화합니다.

```python
token.lower()
```

이 방식은 과제에서 요구하는 키워드 추출 기준과 동일합니다.

### 역색인의 장점

전체 커밋 수를 N이라고 할 때, 단순 순회 검색은 검색할 때마다 O(N)의 커밋을 확인해야 합니다.

반면 역색인을 사용하면 키워드 또는 작성자에 해당하는 후보 목록을 바로 가져올 수 있어 검색 단계에서 전체 커밋을 순회하는 비용을 줄일 수 있습니다.

대신 새로운 커밋을 생성할 때 keyword index와 author index를 함께 갱신해야 한다는 관리 비용이 발생합니다.

## 11. 정렬 알고리즘

Python의 기본 정렬 API인 다음 함수는 사용하지 않습니다.

```python
sorted()
list.sort()
```

대신 `sort.py`에서 정렬 알고리즘을 직접 구현합니다.

현재는 **Insertion Sort**를 사용하며, 비교 기준을 함수로 전달하여 정렬 기준을 변경할 수 있도록 구현했습니다.

```text
LOG --sort-by=date
```

에서는 timestamp를 기준으로 정렬하고,

```text
LOG --sort-by=author
```

에서는 author를 기준으로 정렬합니다.

### Insertion Sort

Insertion Sort의 기본적인 동작은 다음과 같습니다.

```text
정렬된 영역에 새로운 값을 하나씩 삽입
↓
앞의 값과 비교
↓
필요하면 값을 이동
↓
모든 값이 정렬될 때까지 반복
```

시간 복잡도는 다음과 같습니다.

| 경우 | 시간 복잡도 |
| -- | ------ |
| 평균 | O(n²)  |
| 최악 | O(n²)  |
| 최선 | O(n)   |

Insertion Sort는 동일한 비교값을 가진 요소의 상대적인 순서를 유지할 수 있는 **안정 정렬(Stable Sort)**입니다.

이번 프로젝트에서는 Python의 기본 정렬 함수를 사용하는 대신 정렬 알고리즘 자체를 직접 구현하는 것이 목적이므로 Insertion Sort를 선택했습니다.

## 13. 설계 구조

전체적인 데이터 흐름은 다음과 같습니다.

```text
                 ┌─────────────┐
                 │   main.py   │
                 │     CLI     │
                 └──────┬──────┘
                        │
                        ▼
                 ┌─────────────┐
                 │  MiniGit    │
                 └──────┬──────┘
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
 ┌────────────┐  ┌────────────┐  ┌────────────┐
 │ Repository │  │   Graph    │  │   Search   │
 └─────┬──────┘  └────────────┘  └────────────┘
       │
       ▼
 ┌────────────┐
 │   Commit   │
 └────────────┘

                 ┌────────────┐
                 │    Sort    │
                 └────────────┘
```

각 모듈의 역할을 분리하여 다음과 같은 구조를 유지합니다.

```text
CLI
 ↓
MiniGit
 ├── Repository
 ├── Graph
 ├── Search
 └── Sort
```

* `Repository`: 저장소 상태와 커밋/브랜치 관리
* `Graph`: 커밋 관계와 탐색 알고리즘
* `Search`: 역색인과 검색
* `Sort`: 정렬 알고리즘
* `MiniGit`: 각 모듈을 연결하는 서비스 계층
* `main`: 사용자 입력과 출력 담당

이러한 구조를 통해 알고리즘 로직을 CLI 코드와 분리하고, 각각의 기능을 독립적으로 테스트할 수 있도록 구성했습니다.

## 14. 시간복잡도 및 확장성

현재 구현은 학습 목적의 메모리 기반 Mini Git이므로 커밋 수가 매우 커지는 상황까지 최적화하지 않았습니다.

주요 병목 가능성은 다음과 같습니다.

### PATH

현재 무방향 그래프에서 자식 노드를 찾기 위해 저장된 모든 커밋을 확인합니다.

```text
현재 커밋
   ↓
부모 확인
   +
전체 커밋을 순회하여 자식 확인
```

따라서 커밋 수가 증가하면 이웃 탐색 비용도 증가할 수 있습니다.

개선 방법으로는 별도의 `children` 인덱스를 유지하여 부모 → 자식 관계를 빠르게 조회하도록 만들 수 있습니다.

### LOG

현재 위상 정렬 과정에서 각 커밋의 자식 관계를 찾기 위해 커밋 전체를 확인합니다.

대규모 저장소에서는 부모 → 자식 관계를 별도로 저장하면 반복적인 전체 순회를 줄일 수 있습니다.

### SEARCH

역색인을 사용하여 전체 커밋 순회를 줄였지만, 하나의 키워드에 매우 많은 커밋이 연결되면 결과 목록 자체가 커질 수 있습니다.

대규모 시스템에서는 인덱스를 분할하거나 저장 구조를 개선하는 방법을 고려할 수 있습니다.

### 정렬

현재 Insertion Sort는 평균 및 최악의 경우 O(n²)이므로 커밋 수가 많아질수록 정렬 비용이 커질 수 있습니다.

실제 대규모 시스템에서는 Merge Sort, Heap Sort, Quick Sort 등의 알고리즘을 고려할 수 있습니다.

또한 검색 인덱스나 데이터를 여러 서버로 분산하거나 **sharding**하는 방식으로 데이터 규모를 확장할 수도 있습니다.

현재 프로젝트에서는 이러한 최적화보다는 자료구조와 알고리즘의 직접 구현 및 이해를 우선합니다.

## 15. 에러 처리

잘못된 입력에 대해서는 최소한의 표준화된 에러 메시지를 사용합니다.

예:

```text
Invalid args

No path
```

CLI에서는 명령어의 대소문자를 구분하지 않으며, 문자열 인자에 공백이 포함되는 경우 따옴표를 사용할 수 있습니다.

```text
INIT "Alice"
COMMIT "Add login feature"
```

옵션은 다음 형식을 사용합니다.

```text
SEARCH --author=<name>
LOG --sort-by=date
LOG --sort-by=author
```

## 18. 프로젝트를 통해 이해한 설계 포인트

이 프로젝트에서는 단순히 Git 명령어를 흉내 내는 것보다 Git 내부 구조를 자료구조와 알고리즘 관점에서 구현하는 데 중점을 두었습니다.

특히 다음과 같은 관계를 직접 구현했습니다.

```text
Git Commit
    ↓
DAG
    ↓
DFS / BFS / Topological Sort
    ↓
커밋 관계 탐색

Commit Metadata
    ↓
Inverted Index
    ↓
Keyword / Author Search

Commit List
    ↓
Insertion Sort
    ↓
Date / Author Ordering
```

이를 통해 Git과 같은 버전 관리 시스템이 단순히 파일을 저장하는 프로그램이 아니라 **그래프, 인덱스, 정렬 및 탐색 알고리즘이 결합된 시스템**이라는 점을 이해하는 것을 목표로 했습니다.
